# Deep analysis of the dump-truck simulation model and generated data

**Document purpose:** explain every modeled configuration, operating state,
fault/degradation state, major attribute relationship, health calculation and
RUL calculation in the current project. It also separates **implemented model
causation** from **statistical correlation** and from claims that the current
synthetic data cannot support.

**Evidence reviewed:**

- `telemetry_model.py` — legacy dump-truck digital-twin simulator.
- `generate_dataset.py` — all-combination C-WTVC CSV generator.
- `operational_ranges.py` — Green/Amber/Red classifier.
- `analysis/analyse_dataset.py` and `analysis/results_no_perception/` —
  correlation, feature-selection, PCA and held-out validation outputs.
- `engine_lab/simulation.py`, `engine_lab/analytics.py` and
  `engine_lab/workflow.py` — CPAI-style evidence-lab simulator and
  observation-only analysis path.
- `FAULT_SIGNATURE_ALIGNMENT.md` — comparison against the supplied fault
  signature matrix.

> **Important interpretation:** this project contains two related but separate
> simulation paths. The legacy path generates the 164,160-row dump-truck
> dataset and its health/RUL targets. The Engine Evidence Lab generates timed
> test-bench-style observations and performs state-conditioned diagnostics. The
> two paths must not be presented as one calibrated physical model.

## 1. Executive conclusion

The project is a **transparent synthetic digital twin**, not a validated engine
prognostics system. It has three useful layers:

1. **Context and physics-inspired generation:** payload, route, mode, demand,
   thermal, lubrication, driveline, braking, suspension, structural, inertial
   and perception signals are generated by explicit equations with bounded
   noise.
2. **Rule-based health and planning RUL:** the legacy engine-health score is a
   weighted penalty function; RUL is an algebraic transformation of that score.
3. **Evidence-lab inference:** expected healthy readings are conditioned on
   operating context, residuals are calculated, persistent deviations are
   screened, and hypotheses remain unconfirmed until technician evidence is
   recorded.

The generated data therefore demonstrates that a model can learn or reproduce
the simulator's internal rules. It does **not** demonstrate that the same
attributes predict actual failure, physical remaining life, or a confirmed
root cause on a Cat 793F or another real truck.

### Main findings

- The legacy dataset has **164,160 rows = 960 configurations × 171 samples**.
- The 960 configurations are 3 scenarios × 5 payload classes × 2 start
  conditions × 32 static manual-fault combinations.
- Each 171-sample journey is one 1,800-second trajectory including both
  endpoints; it is not 171 independent journeys or 171 independent life
  histories.
- The no-perception analysis used 74 unique numeric telemetry inputs, reduced
  them to 33 correlation-pruned inputs, selected 16 original inputs, and found
  a 14-component PCA representation retaining 95.13% input variance.
- On the untouched synthetic test groups, the 16-input model obtained health
  MAE 8.074 points, health R² 0.568, RUL MAE 1,125.578 hours and RUL R² 0.583.
- The health and RUL targets are generated by the simulator itself. The above
  scores are therefore **rule imitation**, not field prognostic accuracy.

## 2. Model architecture and data layers

### 2.1 Legacy dump-truck path

```text
configuration
  -> route / drive-cycle context
  -> payload and stress
  -> engine and driveline
  -> brakes, suspension, frame and IMU
  -> GNSS, LiDAR, radar and DSS
  -> derived fault flags
  -> rule-based engine health
  -> algebraic planning RUL and action
  -> flattened CSV row
```

The legacy path is implemented primarily by `simulate_journey()` in
`telemetry_model.py`. `generate_dataset.py` then applies each selected manual
fault to every frame in a journey, recalculates health, and flattens nested
telemetry into CSV columns.

### 2.2 Engine Evidence Lab path

```text
engine/test configuration + timed schedules
  -> healthy context reference
  -> latent physical state and wear
  -> observed sensor values
  -> observation-only residual analysis
  -> data quality, anomalies, hypotheses and actions
  -> optional gated RUL assessment
```

The Evidence Lab keeps four concepts separate:

| Layer | Meaning | Used by diagnosis? |
|---|---|---:|
| Observations | Sensor-like measured values and quality | Yes |
| Context | RPM, demand, ambient, elapsed time, transient and start state | Yes |
| Truth | Hidden schedule, fault phase and latent wear | No |
| Predictions | Residuals, anomalies, hypotheses, health and action | Output |

This separation is essential: a diagnosis must not read the injected fault
label and merely repeat it.

## 3. All legacy configuration states

### 3.1 Scenario states

| State | Meaning and modeled effect | Health/RUL effect |
|---|---|---|
| `ideal` | Nominal route conditions; baseline stress is low. | No scenario penalty; normal algebraic RUL. |
| `stress` | Stress rises through the journey and affects load, temperature, vibration, driveline, braking, structure and perception. | Health penalty `5 + 0.27 × stress_level_pct`; RUL multiplier `0.88`. |
| `overhaul` | Post-service transient; thermal/oil residual terms fade with progress. | Small temporary health penalty; RUL multiplier `1.04`, capped at design life. |

The `normal` and `maintenance` names are aliases for `ideal` and `overhaul`.

### 3.2 Payload states

Payload class is a **fixed journey category**. It is not supposed to change
inside a loaded journey.

| Class | Utilisation | Meaning |
|---|---:|---|
| `empty` | 0% | Empty or unloaded truck. |
| `light` | 48% | Light load. |
| `medium` | 72% | Nominal/standard load. |
| `heavy` | 94% | Near rated capacity. |
| `overload` | 108% | Above rated capacity; `payload.over_capacity = true`. |

The payload mass is calculated as:

```text
payload_mass_t = rated_capacity_t × utilization_ratio
payload_utilization_pct = 100 × utilization_ratio
```

Payload is a context variable. It increases demand, traction mass, suspension
compression, frame strain, thermal loading and health penalties, but it is not
the same thing as instantaneous engine load.

### 3.3 Start states

| State | Modeled meaning |
|---|---|
| `warm` | Initial oil/coolant are near normal operating temperature. |
| `cold` | Thermal states begin near ambient and require warm-up; C-WTVC uses a cold-decay term. |

Cold start changes warm-up transients, RPM command, effective power, fuel
consumption, energy split, coolant flow and thermostat response. It should not
be interpreted as a fault by itself.

### 3.4 Drive-cycle states

| Drive cycle | Meaning |
|---|---|
| `synthetic_route` | Compact route with explicit truck modes such as parking, idle, hauling, upslope, downslope, braking and dumping. |
| `c-wtvc` | Research proxy with urban 0–900 s, highway 900–1368 s and expressway 1368–1800 s phases. |

The generated dataset uses the C-WTVC proxy with `num_steps=171` and
`timestep_s = 1800 / 170 ≈ 10.588 s`.

### 3.5 Operating mode states

| Mode | Physical interpretation | Main generated relationships |
|---|---|---|
| `parked` | No travel; parking brake may be applied. | Near-zero speed/load; low engine demand. |
| `idle` | Engine running at low demand. | Load constrained to 5–28% in the legacy engine path; C-WTVC uses approximately 4–20%. |
| `hauling` | Normal loaded travel. | Speed, engine load, torque, traction and thermal values rise with route and payload. |
| `upslope` | Positive grade / climbing. | Mode penalty, higher stress, pitch, traction power and driveline demand. |
| `downslope` | Negative grade / descending. | Lower grade traction demand; braking/coasting context can still heat brakes. |
| `braking` | Active braking. | Brake pedal, line pressure, disc temperature, stroke and ABS state change. |
| `dumping` | Dump-body operation. | Hoist/body position changes; operational context differs from hauling. |

The C-WTVC proxy primarily uses idle, hauling and downslope-like phases; the
compact route is the path that explicitly exercises the full operating-mode
set.

## 4. Telemetry domains and attribute relationships

The flattened CSV contains 202 columns, but many are aliases, nested copies,
derived outputs, labels or constants. The main telemetry domains are:

| Domain | Important attributes | Causal role in the model |
|---|---|---|
| Context/payload | scenario, mode, payload class, mass, utilization, stress, elapsed time | Upstream drivers of demand and exposure. |
| Engine | RPM, load, torque, power, coolant/oil temperature, oil pressure, fuel rate/level, boost, exhaust, vibration | Primary engine condition and health inputs. |
| Energy flow | Fuel energy, coolant energy, exhaust energy, mechanical/remainder losses | Explains energy partition and thermal response. |
| Transmission | Gear, input/output RPM, slip, oil pressure/temperature, efficiency, axle temperature, vibration | Driveline efficiency, pressure and wear proxies. |
| Brakes | Pedal, line pressure, disc temperature, pad wear, stroke, accumulator pressure | Braking load and brake condition. |
| Suspension | Compression, hydraulic pressure/condition, shock temperature, actuator vibration, corner pressures | Load transfer, ride/actuator condition and overload. |
| Frame | Strain, stress, deflection, twist, fatigue index | Structural load and rollover/strain indicators. |
| IMU | Accelerations, angular rates, roll/pitch/yaw, vibration | Vehicle motion, vibration and stability context. |
| GNSS/GPS | Position, altitude, speed, heading, accuracy, satellites, fix type | Navigation and route context; not engine-health evidence. |
| LiDAR/radar | Distance, confidence, object count, sensor status | Perception and obstacle context. |
| DSS/camera | Collision, rollover, overspeed, fatigue, distraction, camera state | Driver and safety decisions; not an engine-health target. |

### 4.1 Engine and driveline equations

For the compact route, the principal relationships are:

```text
engine_load_pct ≈ 100 × (0.10 + 0.72 × mode_load
                           + 0.16 × max(0, utilization_ratio − 0.5))
                  + 14 × stress_ratio + noise

RPM ≈ clamp(680 + 16 × engine_load_pct + noise, 600, 2200)
torque_Nm ≈ clamp(90 + 23 × engine_load_pct + noise, 0, 2700)
power_kW = torque_Nm × RPM / 9549
```

For C-WTVC, traction power combines inertial, grade, aerodynamic and rolling
resistance terms:

```text
m = base_vehicle_mass + payload_mass
P_traction_kW = [m·a·v + m·g·grade·v + 0.5·rho·Cd·A·v³
                 + Crr·m·g·v] / 1000

effective_power_kW = clamp(P_traction / 0.88 + 18 + 32 × cold_decay,
                           12, 420)
load_pct ≈ 100 × effective_power / 420 + 8 × stress_ratio + noise
torque_Nm = 9549 × effective_power / RPM
```

These equations create the causal relationship:

```text
payload + grade + acceleration + speed
  -> traction power
  -> effective engine power
  -> load, torque and fuel demand
  -> temperature, vibration, energy flow and health penalties
```

### 4.2 Thermal, lubrication and exhaust equations

Compact-route terms include:

```text
coolant_temp_C ≈ 72 + 0.21 × load_pct + 26 × stress_ratio
                 + overhaul_thermal_residual + noise

oil_temp_C ≈ 68 + 0.20 × load_pct + 20 × stress_ratio + noise

oil_pressure_kPa ≈ clamp(485 − 0.20 × load_pct − 32 × stress_ratio
                         + overhaul_oil_residual + noise, 280, 540)

vibration_RMS_g ≈ clamp(0.035 + 0.0014 × load_pct
                         + 0.27 × stress_ratio + noise, 0.01, 1.2)

exhaust_temp_C ≈ clamp(190 + 4.1 × load_pct + 170 × stress_ratio + noise,
                        120, 850)
```

In C-WTVC, fuel flow is obtained from brake-specific fuel consumption:

```text
BSFC ≈ 210 + 35 × (1 − load_pct/100)²
       + 20 × cold_decay + 12 × transient_index

fuel_mass_flow = BSFC × effective_power / 3,600,000
fuel_energy_kW = fuel_mass_flow × 42.5 MJ/kg / 1000
fuel_rate_L/h = fuel_mass_flow × 3600 / fuel_density
```

The energy model then allocates fuel energy:

```text
coolant_energy = fuel_energy × coolant_fraction
exhaust_energy = fuel_energy × exhaust_fraction
mechanical_loss ≈ 0.09 × fuel_energy
remainder_loss = fuel_energy − effective_power − coolant_energy
                 − exhaust_energy − mechanical_loss
```

The thermostat and coolant-flow states are first-order lag models. Cold start
uses a slower flow time constant and a slower coolant mean-temperature target;
this creates a causal warm-up lag rather than an arbitrary cold-start label.

### 4.3 Transmission equations

```text
slip_pct ≈ 0.5 × stress_pct / 10
           + 3 if mode = upslope
           + noise

efficiency_pct ≈ 99 − 0.45 × slip_pct
output_torque ≈ engine_torque × (1 − slip_pct/100)

powertrain_pressure_bar ≈ 18 + 0.12 × load_pct
                          − 8 × stress_ratio + noise

gearbox_vibration ≈ 1.4 + 0.18 × slip_pct
                    + 0.8 × stress_ratio + noise
```

The model therefore makes transmission pressure, slip, efficiency, vibration
and output torque mutually related. A low pressure and high vibration pair is
not independently generated as a gearbox-seal failure in the legacy path; it is
mostly a load/stress relationship unless a new scheduled fault is added.

### 4.4 Brakes, suspension and frame equations

```text
brake_disc_temp ≈ 35 + 0.75 × pedal + 80 × stress_ratio + noise
pad_wear ≈ base_wear + scenario_wear × progress
            + 8 if braking + noise
stroke_pct ≈ 0.76 × pedal + 0.18 × pad_wear + noise

suspension_compression ≈ 63 × utilization_ratio
                         + 20 × mode_load + 14 × stress_ratio + noise
hydraulic_pressure ≈ 105 + 1.25 × compression
                    + 25 × stress_ratio + noise
shock_temp ≈ 34 + 0.30 × compression + 30 × stress_ratio + noise
hydraulic_condition ≈ 98 − 0.10 × compression − 8 × stress_ratio + noise
actuator_vibration ≈ 1.6 + 10 × engine_vibration + 1.2 × stress_ratio + noise

frame_strain ≈ 45 + 440 × utilization_ratio + 220 × mode_load
                + 610 × stress_ratio + noise
frame_stress_MPa ≈ 0.12 × frame_strain
deflection_mm ≈ 0.045 × compression + frame_strain/1500
fatigue_index_pct ≈ 5 + frame_strain/17
```

These are physically plausible directional relationships, but they are not
calibrated material, tyre, brake, hydraulic or suspension models.

### 4.5 IMU and perception relationships

IMU pitch follows operating mode (`+8°` upslope, `−5°` downslope, `−2°`
braking), while roll and angular rates include route oscillation, vibration and
stress-dependent noise. GNSS accuracy degrades with stress. LiDAR confidence,
point count and scan rate fall as stress increases; radar may be faulted at
high stress. DSS alerts are derived from obstacle distance, frame strain,
speed, route state and stress.

These signals are important for safety and control, but they should not be
removed from a real deployment because a synthetic engine-health analysis ranks
them low.

## 5. All legacy fault and condition states

### 5.1 Automatically derived fault flags

| Flag | Trigger in current simulator | Main attributes affected |
|---|---|---|
| `engine_overheat` | coolant temperature ≥108 °C | coolant temperature, health and RUL |
| `low_oil_pressure` | engine oil pressure ≤250 kPa | oil pressure, health and RUL |
| `transmission_slip` | slip ≥8% | slip, efficiency, output torque, vibration |
| `brake_wear` | pad wear ≥70% | pad wear, stroke, brake temperature |
| `suspension_overload` | compression ≥72% | compression, pressures, shock temperature |
| `frame_strain` | strain ≥900 µstrain | frame stress, fatigue, DSS rollover logic |
| `gnss_degraded` | GNSS accuracy ≥3.5 m | navigation quality |
| `lidar_obstructed` | LiDAR blocked by stress condition | obstacle perception |
| `radar_fault` | radar sensor not OK | target confidence/object detection |
| `imu_fault` | IMU vibration RMS ≥0.65 g | motion/vibration quality |
| `payload_overload` | utilization >100% | payload, suspension, frame and health |
| `dss_alert` | any DSS collision/rollover/overspeed/fatigue alert | safety action, not root-cause diagnosis |

These are threshold flags, not independent failure labels. A threshold crossing
can be caused by scenario, payload, route state, a manual fault, or noise.

### 5.2 Manual static injections in `generate_dataset.py`

| Injection | Transformation applied to every sample | What it does not model |
|---|---|---|
| `overheat` | Adds 29 °C coolant/pump temperature, 21 °C oil temperature and 85 °C exhaust temperature; reduces hydraulic condition. | No onset, progression, recovery, pump-flow mechanism or independent cause diagnosis. |
| `bearing_failure` | Adds engine/IMU/block/transmission vibration. | No bearing wear trajectory, frequency spectrum, oil-condition change or dedicated bearing label. |
| `low_oil` | Subtracts 155 kPa oil pressure and 13 percentage points oil level. | Oil level is not oil condition; no pump-flow or bearing-clearance mechanism. |
| `brake_wear` | Adds pad wear, stroke, disc/oil/cooling temperatures. | No brake degradation trajectory or independent brake-life label. |
| `perception_degraded` | Degrades GNSS, LiDAR and radar. | No detailed sensor-noise, bias, drift, latency or camera model. |

Because these injections are applied to every frame, they are **static
scenario variants**, not temporal fault events.

## 6. Engine Evidence Lab states and fault schedules

### 6.1 Inferred operating states

The Evidence Lab derives state from observed context, not from hidden fault
truth:

| State | Rule |
|---|---|
| `transition` | `context.transient` is true/nonzero. |
| `cold_warmup` | Cold start and elapsed time <180 s. |
| `steady_idle` | RPM ≤850 and demand ≤15%. |
| `steady_loaded` | Valid context not matching the above states. |
| `unknown` | Context is missing, invalid, inconsistent or outside bounds. |

Thresholds are widened during transition and cold warm-up so normal transient
behaviour is less likely to become a false anomaly.

### 6.2 Scheduled fault kinds

| Fault kind | Latent effect |
|---|---|
| `lubrication_degradation` | Gradual lubrication wear; lower pressure and higher oil temperature/vibration. |
| `oil_starvation` | Stronger pressure loss, especially during transients; increases bearing wear. |
| `bearing_degradation` | Increased vibration and oil-temperature/pressure effects. |
| `cooling_restriction` | Lower coolant flow and higher coolant temperature; EGT also rises. |
| `thermostat_malfunction` | `delayed`, `stuck_open` or `stuck_closed`; modifies thermostat, flow and coolant temperature. |
| `combustion_imbalance` | EGT cylinder imbalance and vibration changes. |
| `sensor_fault` | Observation-only `frozen`, `biased` or `missing` value; no physical wear. |
| `incomplete_overhaul` | Temporary post-service settling and additional bearing/lubrication stress. |

### 6.3 Event envelope and severity

For an event beginning at `onset_s`, with duration `D`, recovery `R`, base
severity `s` and progression `p`:

```text
active_fraction = age / D
active_level = clip(s × (1 + p × active_fraction), 0, 1)

recovery_level = active_terminal_level × (1 − recovery_age / R)
```

The simulator supports recurrence and overlapping events; the strongest active
envelope is used. This is more realistic than the legacy all-frames injection.

### 6.4 Wear propagation

Wear state is represented by lubrication, bearing, cooling and combustion
components. With load factor `L` and time step `dt`, the model updates:

```text
wear_next[k] = clip(wear[k] + dt × L × (base_rate[k] + fault_rate[k]), 0, 1)
```

Fault-dependent rates include:

```text
lubrication_rate = 0.00032×lubrication_degradation
                 + 0.00065×oil_starvation

bearing_rate = 0.00042×bearing_degradation
             + 0.0008×starvation
             + 0.00022×lubrication_degradation
             + 0.0006×incomplete_overhaul

cooling_rate = 0.00028×cooling_restriction
             + 0.00018×thermostat_malfunction

combustion_rate = 0.0003×combustion_imbalance
```

The latent state then changes pressure, temperature, vibration, coolant flow,
thermostat opening and EGT imbalance. Sensor faults are applied after physical
generation and therefore do not create mechanical wear.

## 7. Operational Green/Amber/Red conditions

`operational_ranges.py` classifies each value independently. Green means the
reading is within the explicitly supplied normal band; amber means caution or
an uncovered gap; red means outside the specified safe band.

| Indicator | Green | Amber | Red |
|---|---|---|---|
| Engine block temperature | 82–<101 °C | 101–108 °C; also 78–82 °C gap | <78 or >108 °C |
| Engine oil temperature | 86–<100 °C | 100–106 °C | >106 °C |
| Exhaust temperature | 340–<555 °C | 555–615 °C | >615 °C |
| Engine oil pressure | >459–<512 kPa | 440–459 or 512–525 kPa | <440 or >525 kPa |
| Engine block vibration | 2–<6.3 mm/s | 6.3–7.5 mm/s | >7.5 mm/s |
| Gearbox oil temperature | 67–<89 °C | 89–96 °C | >96 °C |
| Transmission pressure | >329–<372 kPa | 310–329 or 372–390 kPa | <310 or >390 kPa |
| Gearbox vibration | 1.4–<5 mm/s | 5–6 mm/s | >6 mm/s |
| Hydraulic oil condition | ≥90% | 80–<90% | <80% |
| Hydraulic actuator vibration | 1.6–<5.3 mm/s | 5.3–6.3 mm/s | >6.3 mm/s |
| Coolant pump temperature | 78–<92 °C | 92–98 °C | >98 °C |
| Coolant condition | ≥90% | 80–<90% | <80% |

The classifier conservatively returns amber for NaN, non-covered gaps and
unknown intervals. These operational classifications are separate from the
health score; a frame can be operationally amber while still receiving a fair
or good health score, or vice versa.

## 8. Health-score causation and RUL propagation

### 8.1 Legacy health score

The legacy score starts at 100 and subtracts penalties:

```text
H_raw = 100
        − scenario_penalty
        − high_load_penalty
        − coolant_penalty
        − oil_pressure_penalty
        − vibration_penalty
        − payload_penalty
        − mode_penalty
        − sum(active_fault_weight)

H = clip(H_raw, 0, 100)
```

Exact terms are:

```text
scenario_penalty:
  stress     = 5 + 0.27 × stress_level_pct
  overhaul   = max(0, 2 + 0.03 × stress_level_pct)
  ideal      = 0

high_load_penalty       = 0.10 × (engine_load_pct − 75), if load >75
coolant_penalty         = 0.32 × (coolant_temp_C − 95), if temp >95
oil_pressure_penalty    = 0.08 × (300 − oil_pressure_kPa), if pressure <300
vibration_penalty       = 18 × (vibration_RMS_g − 0.25), if vibration >0.25
payload_penalty         = 0.12 × (utilization_pct − 85), if utilization >85
mode_penalty            = 1.5 for upslope; 0.5 for braking; otherwise 0
```

Active fault weights are:

| Fault | Weight |
|---|---:|
| Engine overheat | 12.0 |
| Low oil pressure | 10.0 |
| Transmission slip | 5.0 |
| Brake wear | 2.0 |
| Suspension overload | 4.0 |
| Frame strain | 7.0 |
| GNSS degraded | 0.5 |
| LiDAR obstructed | 0.5 |
| Radar fault | 0.5 |
| IMU fault | 3.0 |
| Payload overload | 8.0 |
| DSS alert | 1.0 |

Health classes and default actions:

| Score | Class | Action |
|---:|---|---|
| ≥90 | Excellent | Continue operation and scheduled service. |
| 75–<90 | Good | Continue operation and trend parameters. |
| 60–<75 | Fair | Schedule inspection; monitor temperature and oil pressure. |
| 40–<60 | Poor | Plan corrective maintenance before the next shift. |
| <40 | Critical | Stop safely and perform immediate service. |

Because terms are additive, the score is an **engineering prioritisation
index**, not a probability of failure. It can double-count related causes; for
example, high temperature can reduce the score directly and also activate
`engine_overheat` with a separate fixed penalty.

### 8.2 Legacy RUL

The legacy planning estimate is:

```text
RUL_base_hours = design_life_hours × (H / 100)^1.35

RUL_hours = RUL_base_hours × 0.88       if scenario = stress
RUL_hours = min(design_life_hours,
                RUL_base_hours × 1.04)  if scenario = overhaul
RUL_hours = RUL_base_hours              if scenario = ideal
```

The default design life is 12,000 hours. The RUL range shown in the dashboard
is a deterministic health-band interval (approximately ±8%, ±18% or ±28%);
it is not calibrated uncertainty. Since RUL is a deterministic function of
health and scenario, any model predicting RUL is partly learning the health
formula, not an independently observed failure-time process.

### 8.3 Evidence-lab health

For each signal, the Evidence Lab calculates:

```text
residual_signal = observed_signal − expected_healthy_signal(context)
```

An anomaly exists when the absolute residual exceeds a state-conditioned
threshold. A deviation becomes persistent after approximately 15 s for oil
pressure, 30 s for other signals, or 45 s during transitions. Subsystem health
is:

```text
subsystem_health = 100 × [1 − clip(|residual| / threshold / 4, 0, 1)]
overall_health = minimum available subsystem health
```

If required channels are missing, invalid, out of range or frozen, health is
set to unknown rather than silently treating missing evidence as healthy.

The resulting diagnosis contains evidence, alternatives and confirmation
checks, while root cause remains:

```text
Not confirmed — technician evidence required
```

### 8.4 Evidence-lab RUL

The Evidence Lab does not derive RUL from one health score. A numerical RUL is
blocked unless the evidence gates are satisfied:

- at least five longitudinal test summaries;
- one explicit overhaul segment;
- at least 100 operating hours;
- sustained measurable decline;
- current endpoint aligned to the latest history;
- frozen model and explicit failure definition;
- at least 19 independent calibration engine outcomes;
- at least 10 independent held-out test engine outcomes;
- disjoint training, calibration, test and current-engine IDs.

When all gates pass, the interval uses a 90% split-conformal absolute-error
radius from calibration outcomes and an 80% held-out coverage gate. Simulation
evidence is labelled `simulation_only` and is not field validation.

## 9. Correlation, relationship and causation analysis

### 9.1 Pearson correlation

For attributes `X` and target `Y`, the sample Pearson correlation is:

```text
r_xy = Σ_i (x_i − x̄)(y_i − ȳ)
       / sqrt[Σ_i(x_i − x̄)² × Σ_i(y_i − ȳ)²]
```

Interpretation:

- `+1`: perfect positive linear relation;
- `0`: no linear relation;
- `−1`: perfect negative linear relation.

In this project, a positive health correlation means the attribute tends to
increase with the simulator's health score; a negative value means it tends to
increase as health declines. The same applies to RUL.

### 9.2 Spearman rank correlation

Spearman correlation applies Pearson correlation to ranks:

```text
rho_xy = corr(rank(X), rank(Y))
```

It is useful when the relationship is monotonic but not linear, such as a
thresholded or saturating temperature effect.

### 9.3 Partial correlation and confounding

Because payload, scenario, route mode and fault variants are confounders, a
conditional relationship can be estimated by residualising both variables on
controls `Z`:

```text
r_xy·Z = corr(residual(X ~ Z), residual(Y ~ Z))
```

This asks whether `X` and `Y` remain associated after accounting for context.
It still does not prove causation if the model omits a relevant variable or if
the simulator itself imposes the relationship.

### 9.4 Causation versus correlation

The simulator contains structural assignments such as:

```text
payload -> traction mass -> effective power -> load -> temperature
                                            -> fuel and exhaust
                                            -> health

stress -> load/temperature/vibration/braking/frame/perception
       -> automatic flags -> health -> algebraic RUL

manual fault -> modified telemetry -> flags/penalties -> health -> RUL
```

These are **model-imposed causal directions**. A real causal claim requires an
intervention or independent evidence, for example:

```text
average treatment effect of fault F on health
ATE(F) = E[H | do(F=1)] − E[H | do(F=0)]
```

In a synthetic simulator, `do(F=1)` means generating matched trajectories with
the fault mechanism enabled and disabled while holding seed/context constant.
This quantifies the simulator's response to its own intervention. It does not
prove the fault has the same physical effect on a real vehicle.

### 9.5 Feature importance is not causation

The analysis uses ExtraTrees importance. A tree can select a proxy because it
is correlated with a causal variable. Importance can also be split among
redundant channels. PCA loadings are projection coefficients, not causal
effects. A low Pearson correlation does not prove an attribute is unnecessary;
interactions may still be safety-critical.

## 11. Fault-signature matrix alignment

The supplied matrix requires combinations of condition indicators, not merely
single threshold flags. The current status is:

| Matrix condition | Current status |
|---|---|
| Oil pressure down + engine-block vibration up + normal engine-oil condition | Partial: pressure and vibration exist, but oil condition is absent. |
| Piston/ring damage: vibration up + oil temperature up + oil condition down + erratic exhaust | Missing as an explicit fault mechanism and diagnosis. |
| Turbo/exhaust-side fault: isolated exhaust abnormality while block/oil temperatures normal | Missing. |
| Cooling-system failure: block + oil + exhaust + coolant-pump temperatures all up | Partial: overheat raises related temperatures; no independent pump/radiator mechanism. |
| Coolant degradation: pump temperature up + coolant condition down with block near normal | Missing as a scheduled signature. |
| Gearbox seal loss: transmission pressure down + gearbox vibration up + normal gearbox condition | Missing; gearbox condition channel and schedule are absent. |
| Gearbox bearing/gear wear: pressure down + vibration up + condition down | Missing. |
| Hydraulic pump/actuator aging: slow condition decrease + actuator vibration increase | Signals exist, but no scheduled diagnosis/rate evaluator. |
| Hydraulic contamination/filter/seal breach: fast condition decrease + actuator vibration | Missing. |
| Isolated sensor deviation | Partially supported in Evidence Lab; legacy path mostly flags thresholds. |
| Multiple unrelated deviations | Conservative generic anomaly handling exists; no complete matrix evaluator. |

The main schema gaps are:

```text
engine_oil_condition_pct       # not the same as oil_level_pct
gearbox_oil_condition_pct
coolant_condition_rate
engine_oil_condition_rate
gearbox_oil_condition_rate
hydraulic_condition_rate
```

The exact matrix evaluator should require all specified channels, check
persistence and rate, return alternative explanations, and never use hidden
fault schedules or injection labels.

## 12. What each health/RUL relationship means operationally

### High temperature

High coolant, oil or exhaust temperature increases the legacy penalty and may
activate an automatic overheat flag. Sustained temperature elevation can also
indicate cooling restriction, high demand, ambient effects, thermostat
behaviour or a sensor issue. The current model does not independently identify
which cause is true.

### Low oil pressure

Oil pressure below 300 kPa receives a continuous score penalty and ≤250 kPa
activates `low_oil_pressure`. It lowers RUL through the lower health score. The
legacy low-oil injection also lowers oil level, but that is a quantity change,
not a measured oil-condition or pump-wear state.

### Vibration

Vibration above 0.25 g reduces health; high vibration can also activate the IMU
fault flag. In the legacy model, vibration can reflect load/stress, route
motion, synthetic bearing failure or noise. Without frequency-domain features,
it is not sufficient to diagnose a bearing or piston fault.

### Payload and stress

Payload and stress increase demand, temperature, fuel use, suspension
compression, frame strain, braking exposure and perception degradation. They
are upstream confounders for many correlations. A health decrease with payload
does not mean payload itself is a component failure.

### Transmission, brake and hydraulic readings

These attributes can dominate statistical prediction because they carry strong
stress and scenario information. They should drive subsystem-specific health
and maintenance recommendations, not be silently interpreted as engine-root
cause evidence.

### Perception and DSS

Perception faults have low legacy engine-health weights by design. Their low
correlation with engine health does not mean the sensors are unimportant. They
protect against collision, rollover and driver-safety risks and must remain in
an operational safety system.

## 13. Limitations and claims that must not be made

1. **No field validation:** all health, RUL and confidence targets are
   simulator-derived.
2. **No independent failure time:** legacy RUL is not learned from failure
   outcomes; Evidence Lab RUL is gated until independent outcomes exist.
3. **Static legacy faults:** manual faults affect every sample and lack onset,
   progression, recurrence and recovery.
4. **Synthetic confounding:** scenario, payload, mode, time and fault toggles
   are linked by design.
5. **Proxy variables:** coolant temperature is used as an engine-block
   temperature proxy; vibration in g and mm/s are different measurement types.
6. **Incomplete fault signatures:** engine oil condition, gearbox condition,
   piston/ring, turbo, gearbox and hydraulic mechanisms are not fully modeled.
7. **Sampling rate:** approximately 10.6-second C-WTVC samples cannot support
   short pressure transients or bearing-frequency diagnostics.
8. **One seed and one route family:** the current analysis does not establish
   robustness to unseen machines, environments, routes or fault mechanisms.
9. **Confidence is deterministic:** legacy High/Medium/Low confidence uses
   90/75/55 bands from health classification, not calibrated probability.
10. **Feature selection is not sensor deletion:** safety-critical GNSS, IMU,
    LiDAR, radar, camera and DSS channels must not be removed because they rank
    low in an engine-health experiment.

## 14. Recommended next analytical and modeling steps

### Immediate

1. Add oil-condition and gearbox-condition observations separately from oil
   level and pressure.
2. Add timed fault schedules to the dump-truck path, not only all-frame
   toggles.
3. Add condition-rate features and persistence windows.
4. Build a matrix evaluator that requires all signature conditions and reports
   `anomaly`, `probable hypothesis`, `alternatives`, `evidence` and
   `technician confirmation required`.
5. Separate health targets into engine, transmission, brakes, hydraulics,
   structure, perception and overall vehicle health.

### Validation design

For every fault mechanism, generate matched interventions:

```text
same engine parameters + same context + same seed
  -> fault off trajectory
  -> fault on trajectory
  -> paired delta for each signal, health and action
```

Then repeat across independent virtual engines, seeds, ambient conditions,
routes, wear levels and unseen fault severities. Split train/validation/test by
`Engine_ID`, not by rows.

### Field-oriented transition

Before claiming predictive maintenance capability, collect synchronized raw
signals, calibration and quality flags, maintenance/overhaul records,
technician confirmations, failure definitions, operating hours and censored
non-failure histories. Freeze the model before calibration and evaluate on
independent engines.
